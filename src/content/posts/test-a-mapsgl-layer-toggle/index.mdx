Developers have reported [layers staying on screen after state updates](https://github.com/visgl/deck.gl/discussions/6646) and [map styles failing to reflect changed data](https://github.com/alex3165/react-mapbox-gl/issues/418). Those reports involve other map libraries. For this example, I wanted to test the connection between a React control and a MapsGL layer.

I built a Storybook example around a temperature toggle and broke it on purpose. The control uses React state, while Xweather MapsGL manages the weather layer on a Mapbox map. That gives us two places to check after a click.

## Start with the toggle

This is the part of the handler that changes visibility.

```ts
const next = !visible;
instance.setWeatherLayerVisibility("temperatures", next);
setVisible(next);
```

`setWeatherLayerVisibility` tells MapsGL to show or hide the temperature layer. `setVisible` updates the React state that controls the button.

Comment out the MapsGL call and click the button. React updates the control, but you haven't told MapsGL to hide anything.

A test like this still passes.

```ts
await userEvent.click(button);
await expect(button).toHaveAttribute("aria-pressed", "false");
```

That checks the control's accessibility state. We also need to check the weather layer.

```ts
await expect(layer.visible).toBe(false);
```

With the MapsGL call missing, this assertion fails with `expected true to be false`. You can see that happen in the recording below.

## Wait for weather data

Before clicking anything, we need a loaded map.

I set the camera over Minneapolis and added one temperature layer. The component creates the map and controller, then checks readiness during Mapbox render events.

```ts
if (!instance.isReady || instance.isLoading) return;

const layer = instance.getWeatherLayer("temperatures");
if (!layer || Array.isArray(layer) || !layer.visible) return;

const sample = layer.queryFeatures(
  CENTER,
  map.getZoom(),
  false,
  false
);

if (!sample || sample.nodata || !Number.isFinite(sample.value)) {
  return;
}
```

The temperature sample matters here. Having a controller instance doesn't tell us whether it has received weather data. Querying the map center gives us a value to check before starting the test.

Once those checks pass, the component calls `onReady` with the MapsGL controller. If loading fails or takes longer than 45 seconds, it displays an error.

This avoids adding a fixed delay and hoping the map finishes loading before we click.

## Click the button in Storybook

Storybook's [play function](https://storybook.js.org/docs/8/writing-stories/play-function) lets us run the interaction in the browser alongside the component.

The example uses Storybook 8.6 and `@storybook/test`. I pass `fn()` as the story's `onReady` callback so the test can inspect the controller after loading. These excerpts come from the [complete toggle story](https://github.com/wil-gerard/mapsgl-storybook-testing).

First, wait for either the ready message or an error.

```tsx
const canvas = within(canvasElement);

await waitFor(() => {
  expect(
    canvas.queryByRole("alert") ??
      canvas.queryByText("Weather map ready")
  ).not.toBeNull();
}, { timeout: 60000 });

if (canvas.queryByRole("alert")) {
  throw new Error("Weather map failed to load");
}
```

Then get the layer from the controller supplied to `onReady`.

```tsx
await expect(args.onReady).toHaveBeenCalledTimes(1);
if (!args.onReady) throw new Error("Expected a readiness callback");

const controller = args.onReady.mock.calls[0][0];
const layer = controller.getWeatherLayer("temperatures");

if (!layer || Array.isArray(layer)) {
  throw new Error("Expected one temperature layer");
}
```

Now we can click and check both states.

```tsx
const button = canvas.getByRole("button", {
  name: "Temperature layer",
});

await userEvent.click(button);
await expect(button).toHaveAttribute("aria-pressed", "false");
await expect(layer.visible).toBe(false);

await userEvent.click(button);
await expect(button).toHaveAttribute("aria-pressed", "true");
await expect(layer.visible).toBe(true);
```

The second click checks that we can show the temperatures again. I also check that the handler kept the same layer instance.

```tsx
await expect(
  controller.getWeatherLayer("temperatures")
).toBe(layer);
```

MapsGL provides [`setWeatherLayerVisibility`](https://www.xweather.com/docs/mapsgl/reference/map-controller) for this, so the toggle can reuse the layer.

## Try breaking it

The [example repo](https://github.com/wil-gerard/mapsgl-storybook-testing) includes the component, complete stories, and setup instructions. You'll need a Mapbox token and Xweather credentials with MapsGL access.

Build Storybook and serve the build.

```sh
npm run build-storybook
python3 -m http.server 6007 --bind 127.0.0.1 --directory storybook-static
```

In another terminal, run the map tests.

```sh
npm run test:maps -- --url http://127.0.0.1:6007
```

Run them once with the working handler. Then comment out `setWeatherLayerVisibility`, rebuild Storybook, and run them again.

The load test should still pass. In the toggle test, the button check passes and the layer visibility check fails. Restore the call and rebuild to get the passing result back.

I ran that failure and recovery in Chromium with MapsGL 1.10.2 and Mapbox GL JS 3.32.0 on October 7, 2026.

## Checking the picture too

We've checked that clicking the control changes the layer's visibility setting. We haven't checked the colors or whether the GPU drew the weather tiles correctly.

For those checks, I'd add screenshot comparisons with controlled weather data and a fixed camera. You also need a consistent browser and rendering environment, which [Playwright covers in its visual comparison guide](https://playwright.dev/docs/test-snapshots).

This example uses live weather services, so credentials and network access can affect the run. If it fails during loading, check the loading error before investigating the toggle handler.
